# 第二路线试验：三组配置 × 四个独立长宏

**状态：完成了离线存储核心原型、集成审查和后续嵌套打包验证，未完成整机接入，没有可刷扩容BUP。** 新进展见[打包与内存接入记录](container-and-memory-progress.zh-CN.md)。

64步扩展继续暂停。本次用32次完整按下/松开作为实验目标，保留三组板载配置和每组四个独立宏。按原固件计数方式，每个宏预留67条状态记录，包含64次按下/释放变化和3条余量。摇杆方向变化和按键仍然共享这些记录，不能解释成32次完整摇杆转圈。

## 实际完成的代码

`macro_store.c/.h` 是使用V41宏头、6字节记录、CRC16/MODBUS的存储核心，提供：

- 三组参数区、十二个独立宏槽的布局和边界检查；
- 原V41三组3072字节配置数据向新布局的迁移；
- 宏替换、追加记录、读取和容量拒绝；
- 配置数据导出和恢复时的逐项长度/CRC验证。

记录内容按原样保存。模块没有接管手柄输入事件、回放计时、APP协议或Flash驱动，也没有把按键/摇杆含义的转换视为已完成。`ax_store_init`产生的是用于测试的有效空记录，不是可以刷入设备的厂家默认手柄参数。迁移输入源和目标必须是互不重叠的独立缓冲区。

## 新旧布局

| 项目 | V41原版 | 本次原型 |
|---|---:|---:|
| 每个宏内部记录数 | 35 | 67 |
| 每条记录 | 6字节 | 6字节 |
| 每个宏头 | 10字节 | 10字节 |
| 每个宏槽 | 220字节 | 412字节 |
| 每组手柄参数 | 144字节 | 144字节 |
| 每组宏数 | 4 | 4 |
| 每组配置 | 1024字节 | 1792字节 |
| 三组配置数据 | 3072字节 | 5376字节 |
| 连同原对象68字节前缀、12字节后缀的候选总长 | 3152字节 | 5456字节 |

净增加2304字节是**重新安排存储后的差额**。如果保留旧的静态配置对象，再另从堆申请新对象，实际要找到至少5456字节连续可用RAM，另外还需要正常运行余量。不能把“只多2304字节”当成已证明设备堆内存足够。

## 已通过的验证

```sh
make check
make q32s
```

`make check`使用AddressSanitizer和UndefinedBehaviorSanitizer检查实际C代码，覆盖：

1. CRC标准向量；另用审查脚本核对了V41内置CRC查表。
2. 十二个合成旧宏迁移后，参数和原有内容保留。
3. 十二个宏分别填满67条记录，彼此和前后哨兵不被覆盖。
4. 满容量继续追加时拒绝，整个存储对象保持不变。
5. 保存数据导出后恢复一致；截断和CRC损坏被拒绝。
6. 非法配置号、宏号、长度、空指针被拒绝。
7. 一个宏保存64条状态变化，即32次完整点击，实际宏长394字节。

所有旧数据测试输入都是合成样本，没有真实设备的配置备份。这里的“恢复”是C模块导出/读入测试，**不是手柄断电恢复测试**。

使用下载的杰理官方工具链，模块已交叉编译成`ELF32-q32s`：`macro_store.q32s.o`。其`.text`大小为990字节，无外部未定义函数依赖。交叉编译成功只证明工具链可以生成该CPU指令，不能证明可以直接接到原固件调用点。

## 已证实不能原地扩容

原完整配置对象起点为`0x3120`，原长度`0x0c50`，结束于`0x3d70`。新候选总长`0x1550`若仍放在该地址，结束地址会变成`0x4670`。

但原程序已有多处对`0x41b8`、`0x41bc`、`0x4288`和`0x45bc`等地址的使用。它们位于扩大的窗口内。因此原地加大配置会与已有对象冲突，必须迁移或重新布局；不能直接覆盖这些区域。

已经定位到`pvPortMalloc`一类分配器的实现，但没有设备运行中的堆状态、连续可分配空间及高峰用量，不能指定一个可靠的新RAM地址，也不能保证一次5456字节申请不会影响蓝牙、USB和任务栈。

## 固件接入尚需解决的实质问题

- **RAM位置与生命周期**：给新对象分配可靠空间，在第一次读配置前初始化，并在分配不足时停止扩展路径。旧静态区是否可回收需另行证明。
- **地址引用和指令长度**：审查脚本已核对87条候选指令的原始字节。候选清单不是完整覆盖证明；还须查RAM内运行代码和所有内部指针。很多原220字节常数是2字节指令，改成412可能需要更长指令，不能覆盖下一条指令。
- **录制与回放**：35→67、最后一条记录处理、槽间距、长度计算及执行限幅必须同时接入；仅修改结束条件会越界。
- **切换/清除配置**：原程序有按1024步进、左移10位和硬编码循环终点，需逐条核对，尤其工厂重置路径不能机械替换常数。
- **协议缓冲**：D8/D9读写与A4分片重组需能处理新长度。已定位接收函数`0x01e065a0`及其容量比较，并从初始化数据核对四个容量为256/328/256/256字节；运行时扩容和长包接入仍未完成。
- **断电保存**：保存和加载原总长均为`0xc50`，按4KB块处理并有两个块的循环。新候选5456字节需要使用第二块。USERIF描述项为8192字节不等于全部空间都可自由占用；需核对所有权、写入恢复机制、元数据CRC及旧版迁移。
- **重新打包**：八份Flash的固定大小替换、反向还原和4 KiB应用空间增长后端已通过真实原包离线验证。扩容助手代码和跳转接入尚未完成，升级工具对未知尾记录的处理尚未验证。
- **设备验证**：记录满容量、正常回放、摇杆动作、配置切换和断电恢复均未在硬件上测试。

`integration-audit.json`逐项记录这些未解决事项和原指令字节。`audit_original.py`只读，不提供“忽略未解决项并输出可刷包”的选项。

## 后续复核更新

新增加`src/config_image.c/.h`及完整配置迁移测试：从3152字节旧对象迁移到5456字节候选对象，逐字节保留68字节前缀和12字节尾记录。

确认原代码`h[tail+2] = 0x0c00`产生字节`00 0c`，表示尾记录自身的12字节长度；这与三组配置数据恰好也是`0x0c00`字节是两件不同的事。相关元数据常数不能被全局替换为新配置数据大小。启动路径`0x01e0f608`–`0x01e0f60e`亦按12字节验证该尾记录。

新测试覆盖该字节序、整个对象迁移、尾记录/参数CRC错误拒绝，以及失败时不修改目标。硬件Flash驱动、版本识别和上电恢复接入仍未完成。
