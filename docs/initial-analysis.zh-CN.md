# ARMOR-X Pro V41：64步宏修改前的静态分析

历史记录：此文描述最初的64步调研。用户随后暂停64步，并选择保留四个独立宏的第二路线；目前实验目标为32次完整点击。当前进展以仓库根README和第二路线文档为准。

## 当前结论

已成功下载、拆包、解码固件并定位宏的存储、录制、执行和写入路径。尚未生成宏功能修改版，也没有进行设备刷写或硬件验证。

16步不是只改APP界面就能可靠解除的限制。固件确有固定容量：每组配置1024字节，包含144字节手柄参数和4个220字节宏槽。按现有结构扩展四个独立64步宏，会覆盖其他配置和相邻RAM。需要改变数据布局或实现兼容转换，而非仅改变一个比较常数。

用户目标：64步。仍待明确：只需一个背键支持长宏，还是四个背键都分别支持64步；手机APP编辑与手柄直接录制的具体需求也未明确。

## 容器和校验

本体BUP含两套UFW：

1. `XT_XBOX_update_s_v41_20230208.ufw`
2. `XT_XBOX_update_s_v41_20230209.ufw`

每套UFW由35个独立zlib块组成，解压后均为1124288字节。每个UFW又包含`flash.bin`、`flash2.bin`、`flash3.bin`、`flash4.bin`，另有升级引导和元数据。

共检查8份Flash变体，提取的应用程序SHA256完全一致；Flash排列、产品版本字段和编码参数存在差别。八份应用比较记录见`app-image-comparison.json`。

解包时验证了UFW头CRC、目录CRC和Flash载荷CRC；提取应用的JLFS数据CRC为`0x83ca`，与目录记录相符。并非所有元数据项都能直接用原始字节计算其记录的CRC，不能把这一点误认为可忽略所有校验。

`inspect_bup.py`只做离线检查和提取，无设备连接或写入功能。用原始块大小和zlib level 6重建本体BUP，结果逐字节等于原始文件，SHA256一致。这验证的是外层容器，不等于验证修改后固件能够启动、被设备接受或执行64步宏。

命令：

```sh
python inspect_bup.py 'original/01战甲X Pro固件-V41.bup' verified
```

检查结果见`verified/inspection.json`。

## 已定位的固件行为

以下地址为本体应用运行地址；对应`app.bin`文件偏移为“地址减去`0x01e00120`”。证据均使用官方工具`q32s`模式生成。

| 地址 | 静态观察 | 意义 |
|---|---|---|
| `0x01e05ad0` | 配置索引左移10位，然后加基址和`0x44` | 每套板载配置的间距为1024字节 |
| `0x01e05e1e`–`0x01e05e3c` | 配置索引左移10位；宏指针为`0x3120 + index*1024 + 0xd4` | 相对配置参数起点，宏区偏移为`0x90`，即144字节 |
| `0x01e05de4`、`0x01e05e14`、`0x01e05e18` | 宏验证容量`0xdc`，指针每次增加`0xdc`，循环4次 | 4个宏槽，每槽220字节 |
| `0x01e05d96`、`0x01e05d9e` | 清除宏时按`0xdc`定位并清零`0xdc`字节 | 清除路径也依赖固定大小 |
| `0x01e093b6`–`0x01e0941e` | 接收宏时以`0xdc`作验证容量、槽位间距和长度检查 | 录制、执行之外，上传路径也必须处理新容量 |
| `0x01e0a7fc`–`0x01e0a81e` | 槽位索引乘`0xdc`，记录索引乘6 | 宏内部记录是6字节，宏主体偏移10字节 |
| `0x01e0a9c0`–`0x01e0a9ee` | 实际宏长度为`记录数*6 + 10`，然后重算配置CRC | 步数变更涉及长度和CRC |
| `0x01e0d59a`–`0x01e0d5a2` | 录制计数达到`0x23`时调用结束录制路径 | 录制存在35条内部记录的上限 |
| `0x01e0db0e`–`0x01e0db20` | 从`长度-10`除以6计算记录数；大于`0xd7`时限为`0x23` | 执行路径也明确限制35条记录 |

容量关系可以独立复算：

```text
一个宏槽 = 220 = 10字节头 + 35条 × 6字节
一套配置 = 144 + 4 × 220 = 1024字节
三套配置 = 3072字节 = 0x0c00
```

“35条内部记录”不能直接叫“35个APP步骤”。用户按下和释放、按键状态变化可能分别占用记录。若一个APP步骤被编码成按下和释放两条记录，64步至少需要128条记录，即`10 + 128*6 = 778`字节；这个换算仍需核对该APK的实际序列化路径，不能仅凭容量推断视为已证实。

## 两条实现路线及尚未完成的部分

### 单个背键长宏

可以考虑复用原本四槽共880字节的空间：按上述128条记录的假设，778字节可容纳其中。该路线需限制其余宏的读写，处理切换配置、清除宏、执行计数、上传验证、保存和重启恢复；不能只扩大槽0并继续允许其他三个槽照常写入。手机端也需要支持生成和下发长宏。

这是容量上可行的设计方向，不是已完成的补丁。

### 四个背键各有64步

按同一假设，每套配置至少需要`144 + 4*778 = 3256`字节，三套至少9768字节，比当前3072字节多6696字节，尚未计入终止记录、对齐和协议缓冲。固定地址和移位运算散布在程序多处，需要重排或迁移数据存储，并核对运行时可用RAM、持久化存储和协议缓冲。

当前没有完成全程序地址引用分析、所有收发缓冲区容量核对、APK长宏编辑/序列化修改以及设备读回/断电恢复测试，因此不能交付一个可验证的四背键64步刷机包。

## 分析材料

- `inspect_bup.py`：无第三方依赖的V41本体BUP检查、提取及外层往返验证。
- `evidence/*.asm`：配置布局、宏校验、清除、上传、录制和执行上限相关反汇编。
- `unpacked/app-q32s.asm`：完整线性反汇编，含非代码数据区；不能把全文件每一行都当作可达代码。
- `unpacked/controller-0.ufw_unpack/files/app.bin`：提取的原版应用，未修改。
- `app-image-comparison.json`：八份Flash应用的一致性记录。
- `verified/inspection.json`：两个UFW及内部载荷的大小、CRC和SHA256记录。
